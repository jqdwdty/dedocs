Why it exists

OOXML already solves fidelity. It does not solve workflow.

Dedocs exists for builders who want exactness, inspectability, version control, and a better prompt surface than a zip archive.

Raw .docx

Opaque package

Correct for Word, awkward for review, diffing, or AI context.

Unpacked OOXML

Many exact files

Exact but noisy. You inherit archive plumbing and fragmented edits.

Dedocs

One inspectable source

Exact package core, generated guides, semantic transforms, and static proof artifacts.

What it is for

Use it when raw OOXML is exact enough, but not workable enough.

The point is not to replace OOXML’s authority. The point is to give humans and AI a safer, reviewable operating surface on top of it.

Architecture

Three layers, one source of truth.

01

Core package

Every package part is explicit. XML stays UTF-8. Binary stays base64. Untouched content remains exact.

02

Generated guides

Structure summaries help orientation, but they are never promoted to the source of truth.

03

Semantic transforms

Authoring commands compile onto exact package parts and fail loudly when anchors drift.
